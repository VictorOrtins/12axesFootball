# Log real answer vectors to tune the matching on real users

Status: not started (created 2026-11-06). Depends on nothing; best done before any further formula tuning.

## Why

Every number behind the matching comes from simulated users, never real ones:

- Task 14's Optuna tuning used noisy copies of the profiles. Those users were as strong as the profiles, which is why the hub problem was missed.
- The hub fix (`hub-fix` branch) uses `profile-audit/hub_offsets.py`, whose users are "a lean per axis + noisy Likert answers + 30% of axes forced to 50". Those settings (`LEAN_SD`, `ANSWER_NOISE_SD`, `NEUTRAL_AXIS_SHARE`) and `STRETCH_TARGET = 20` were calibrated on **four screenshots** from friends.

With a few dozen to a few hundred real result vectors we could:

1. Check whether real users look like the simulation: intensity, share of axes at 50, which axes go together.
2. Compute `hubOffset` from real users instead of simulated ones, or at least calibrate the simulator on them.
3. Measure the hubs directly: how often each profile is #1 for real people.
4. Re-check `STRETCH_TARGET`, `STRETCH_MAX` and `HUB_PENALTY_WEIGHT`, and give a future Optuna run a real-user objective.

## What exists today

- `POST /api/results` (`QuizController`) receives the submitted answers and returns the result. Nothing is stored: the backend keeps only the JSON catalogs and in-memory caches.
- `GET /api/results/by-axes?v=...` rebuilds a shared result from the 12 values in the URL. These are re-views, not new takes, so **don't log them**: they would count the same person again.
- Hosting: the backend runs on the Render free plan (Docker, `render.yaml`) and sleeps when idle. The disk is **ephemeral** (wiped on every deploy and restart), so a local file is not enough. The frontend runs on Vercel.
- There is no database, no auth and no privacy notice in the app.

## What to store (proposal)

One row per completed quiz (`POST /api/results`), anonymous:

| Field | Why |
|---|---|
| `createdAt`, rounded to the day or hour | spot test bursts, drop old data |
| `variant` (short / extended) and `lang` | users behave differently per variant |
| the 12 axis values (`leftPercent`) | the main thing |
| the raw answers (question id → DT/D/N/C/CT) and archetype choices | lets us recompute vectors if questions or weights change later, and see per-question neutral rates |
| `appVersion` / commit | the questions and formula change between deploys |
| top-1 ideology, team and manager ids (optional) | fast hub count without re-scoring |

Don't store IP addresses, user agents, cookies or any id that links two takes. One person taking the quiz twice counts twice; accept that.

## Where to store it: options

1. **Free managed Postgres (Neon or Supabase free tier).** The backend inserts one row per result. Real SQL, so analysis is easy (`psql` or a CSV export into `profile-audit/`). It needs a JDBC dependency, a connection string as a Render env var, and a schema migration. Free tiers have size and idle limits, but they're far above what we need. *Most work, most useful.*
2. **Render free Postgres.** Same as 1, but the free database expires after about 30 days. Only good for one test round.
3. **Append to an external sheet or form** (Google Sheets API or a form endpoint). No database to run, but credentials sit in the backend, the API is awkward, and rows are harder to query.
4. **Structured log line only** (`log.info("result {json}")`). Almost no code, but Render's free log retention is short and scraping logs is fragile. Fine for a quick one-week experiment, not as the real solution.

Leaning: **1**, with the write done asynchronously and fail-safe. If the insert fails or the database is slow, the user still gets their result; we lose the row, not the request.

## Privacy

- Data is anonymous, but it's still personal-ish behavioural data (LGPD applies to Brazilian users). Add a short line near the quiz or results ("Respostas são salvas de forma anônima para melhorar o matching"), plus a link to a tiny privacy note.
- Consider an opt-out (a checkbox, or `?nolog=1` for testers who don't want to count).
- Keep a retention rule, for example delete rows older than 12 months.

## Analysis side (`profile-audit/`)

- A script that loads the export (CSV or a direct DB read) into an `N × 12` matrix.
- Reports: intensity distribution, share of axes at 50 and per-question neutral rate. The hub report runs on real users (reuse `hub_offsets.hub_report` with `ms.ranking_score`).
- `hub_offsets.py --users <file>`: compute offsets from real vectors, falling back to the simulator when there are too few (pick a minimum, for example 200).
- Compare the real distribution with `simulated_users()`, then re-fit `LEAN_SD`, `ANSWER_NOISE_SD` and `NEUTRAL_AXIS_SHARE`.

## Steps

1. Decide the open questions below.
2. Backend: entity/record, repository, async insert after scoring in `POST /api/results`; env var for the connection string; no-op when it's not set (local dev and tests).
3. Frontend: the privacy line, and the opt-out if chosen.
4. Tests: the result endpoint still answers when the database is down; nothing is written for `by-axes`; nothing is written in tests.
5. Deploy, take the quiz once and check the row.
6. Analysis script plus `--users` in `hub_offsets.py`.
7. After about 100 to 200 real takes: rerun the hub report and update `STRETCH_TARGET` and the offsets if needed. Write up the numbers in `MATCH_EXPLAINED.md`.
